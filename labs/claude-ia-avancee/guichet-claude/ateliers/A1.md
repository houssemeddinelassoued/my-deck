# Atelier 1 · Prompt engineering pour le code

> Jour 1, 10 h 25 – 12 h 00 · 95 minutes · individuel · moteur réel (`claude -p`)

## Objectif

Faire passer la normalisation des demandes de quelques tests verts à **24 / 24 en ne modifiant que le prompt**, puis outiller le choix des exemples et documenter une décision de conception.

## Les fichiers de votre stack

| Rôle | TypeScript | Python | Java | .NET |
|---|---|---|---|---|
| Normalisation (générée) | `ts/src/domaine/normaliser.ts` | `python/guichet/domaine/normaliser.py` | `java/src/main/java/guichet/domaine/Normaliseur.java` | `dotnet/Guichet/Domaine/Normaliseur.cs` |
| Types (à injecter dans le prompt) | `ts/src/domaine/demande.ts` | `python/guichet/domaine/demande.py` | `…/domaine/Demande.java` | `dotnet/Guichet/Domaine/Demande.cs` |
| Choix des exemples | `ts/src/prompts/exemples.ts` | `python/guichet/prompts/exemples.py` | `…/prompts/Exemples.java` | `dotnet/Guichet/Prompts/Exemples.cs` |

Les 24 cas de test sont dans `donnees/normalisation-cas.json` (communs aux 4 stacks).

## La mécanique

```bash
node guichet.mjs generer normaliser v1        # v1, v2, v3… = prompts/normaliser.<version>.md
```

La commande envoie le prompt à Claude par `claude -p` (votre licence), écrit le fichier de normalisation de votre stack, lance les 24 tests et ajoute le score à `resultats.csv`. Un `{{fichier:src/domaine/demande}}` dans le prompt est remplacé par le fichier de types de votre stack. **Vous ne touchez jamais au code à la main.** Option : `--modele haiku` ou `--modele sonnet`.

Si le code généré ne compile pas, le fichier précédent est restauré et la génération est conservée dans `generations/` : lisez-la, c’est instructif.

## Étapes

### A1.1 · Le prompt naïf, et ce qu’il rate (20 min)

1. `node guichet.mjs generer normaliser v1` (le prompt est fourni : il est volontairement pauvre).
2. `node guichet.mjs tests --tag A1.2 --detail` : lisez trois tests rouges.
3. Notez dans `notes/A1.1.md` ce qui manquait **au prompt** (pas au modèle) : signature, formats attendus, cas limites…

Réussite : `node guichet.mjs verifier A1.1` · reprise : `node guichet.mjs reprise A1.1`

### A1.2 · La version structurée (25 min)

1. Créez `prompts/normaliser.v2.md` avec les balises `<contexte>`, `<code_existant>` (avec `{{fichier:src/domaine/demande}}`), `<tache>`, `<criteres>`, `<format_sortie>`.
2. Vos critères doivent être **vérifiables** : chaque ligne doit pouvoir devenir un test.
3. Générez, mesurez. Visez 20 / 24, puis une v3 qui traite les derniers cas (ajoutez les cas limites manquants).

Réussite : `node guichet.mjs verifier A1.2` (≥ 20 / 24) · reprise : `node guichet.mjs reprise A1.2`

### A1.3 · Exemples dynamiques (20 min)

1. Complétez `choisirExemples` dans le fichier « choix des exemples » de votre stack : les trois trous sont marqués `aCompleter` (`a_completer`, `AFaire.completer`, `AFaire.Completer`).
   - score = nombre de mots-clés en commun avec le texte (`motsCles` est fourni) ;
   - tri par score décroissant, **stable** (à égalité, l’ordre du fichier est gardé) ;
   - un seul exemple par type.
2. `node guichet.mjs tests --tag A1.3`
3. Ajoutez une section `<exemples>{{exemples}}</exemples>` dans `prompts/extraction.md`.
4. Comparez : `node guichet.mjs extraire --cas 7 --moteur claude-cli` avec et sans `--sans-exemples`.

Réussite : `node guichet.mjs verifier A1.3` · reprise : `node guichet.mjs reprise A1.3`

### A1.4 · Plan explicite et arbre de pensées (20 min)

Dans l’application Claude, demandez trois conceptions pour **détecter les demandes en double** (même client, même sujet, à quelques heures d’écart), avec un plan explicite pour chacune. Puis :

1. Donnez **vos** critères (coût par demande, faux positifs, maintenance, testabilité…) et leurs poids.
2. Faites noter chaque piste sur ces critères.
3. Remplissez `decisions/doublons.md` : trois pistes, critères, choix argumenté.

Réussite : `node guichet.mjs verifier A1.4` · reprise : `node guichet.mjs reprise A1.4`

## Bonus

Même v3 avec `--modele haiku` puis `--modele sonnet` : le score bouge-t-il ? Et le temps ?

## À retenir

Un prompt se versionne, se teste et se compare comme du code. Ce qui manque presque toujours : le contexte et des critères vérifiables.
