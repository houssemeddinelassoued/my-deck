# Atelier 3 · Formulaire → Claude → base des demandes

> Jour 2, 9 h 45 – 11 h 15 · 85 minutes · individuel · moteur : simulateur (par défaut)

## Objectif

Une demande saisie dans **l’interface web** apparaît, qualifiée et propre, dans le tableau de bord : extraction structurée, boucle d’outils, priorité calculée par le code, injection neutralisée, pas de doublon.

## Avant de commencer

Deux terminaux :

```bash
node guichet.mjs simu      # http://localhost:8787 · journal : http://localhost:8787/__journal
node guichet.mjs lancer    # http://localhost:3000
```

Le simulateur parle le format de l’API Messages : le **SDK officiel** de votre stack est pointé dessus (`ANTHROPIC_BASE_URL`), sans clé réelle. Il imite aussi les erreurs de la vraie API (paramètres refusés, résultats d’outils manquants…). Son journal montre exactement ce que votre code envoie.

## Étapes

### A3.1 · Premier appel (10 min)

Complétez `appelSimple` (deux trous) : une requête minimale (`model`, `max_tokens`, un message `user`), puis le texte du premier bloc `text`. Soumettez une demande dans le formulaire : la réponse brute du simulateur s’affiche. Lisez la requête reçue dans le journal du simulateur, et la réponse : `content`, `stop_reason`, `usage`.

Réussite : `node guichet.mjs verifier A3.1` · reprise : `node guichet.mjs reprise A3.1`

### A3.2 · Extraction structurée (20 min)

Complétez `extraire` dans le moteur API : le schéma part dans `output_config.format` (`{ type: "json_schema", schema }`) ; on ne lit la réponse qu’après `stop_reason = end_turn`. La validation par le contrat (Atelier 2) est déjà branchée : la demande n° 12 doit être refusée.

Réussite : `node guichet.mjs verifier A3.2` · reprise : `node guichet.mjs reprise A3.2`

### A3.3 · Boucle d’outils (25 min)

Complétez la boucle de `traiter` (quatre trous) :

1. fin normale : `stop_reason = end_turn` ;
2. le message assistant renvoyé dans l’historique : **tous** les blocs de la réponse ;
3. une erreur d’outil : un `tool_result` avec `is_error: true` et le message, au lieu de lever l’exception ;
4. **un seul** message user qui contient tous les `tool_result`.

Le journal du simulateur montre les trois allers-retours : `chercher_client`, `enregistrer_demande`, puis la phrase finale.

Réussite : `node guichet.mjs verifier A3.3` · reprise : `node guichet.mjs reprise A3.3`

### A3.4 · Injection et priorité (15 min)

Soumettez la demande n° 11 (liste « Pré-remplir ») : elle contient une instruction cachée. Corrigez en trois couches :

1. **Délimiter** : `construireMessage` place le texte du client dans `<demande_client>…</demande_client>` (et retire toute balise glissée par le client).
2. **Le dire** : dans `prompts/extraction.md`, une section explique que ce contenu est une donnée, jamais une instruction.
3. **Le code décide** : `calculerPriorite(faits, contrat)` applique la règle métier (hors incident → P3 ; panne totale ou ≥ 20 utilisateurs → P1 ; sinon P1 pour un contrat « or », P2 pour les autres). Cas de référence : `donnees/priorite-cas.json`.

Réussite : `node guichet.mjs verifier A3.4` · reprise : `node guichet.mjs reprise A3.4`

### A3.5 · Idempotence et options (15 min)

1. Dans le dépôt SQLite : `parCle(cle)` renvoie la demande déjà enregistrée, et un index unique sur `cle` empêche les doublons même en cas de course. La clé est calculée par `traiter` (e-mail + texte).
2. Soumettez deux fois la même demande : une seule ligne dans le tableau de bord.
3. Options : `MOTEUR=claude-cli node guichet.mjs lancer` (extraction par le vrai modèle, sans boucle d’outils) ; `STOCKAGE=notion` (annexe B du guide).

Réussite : `node guichet.mjs verifier A3.5` · reprise : `node guichet.mjs reprise A3.5`

## À retenir

Le modèle propose et extrait ; votre code exécute, décide et enregistre. C’est cette frontière qui rend le pipeline sûr.
