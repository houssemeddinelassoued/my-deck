# TP 3 · Une suite de tests complète, avec votre première skill

| 3 · Automatiser les tests | 25 min | Matin · vers 12:05 | `tests.instructions.md`, `.github/skills/matrice-de-tests/`, `tests/**` |

## Objectif

Écrire votre méthode de test **une fois**, dans une skill, puis l’appliquer à l’API du TP 2 : matrice de cas, tests unitaires paramétrés, doubles de test, scénarios d’intégration, couverture.

## Point de départ

- L’API du TP 2 et son `copilot-instructions.md`.
- Le framework de test de votre stack, prêt.

## Étapes

1. Créez `.github/instructions/tests.instructions.md` avec `applyTo: "tests/**"` : framework, nommage, Arrange / Act / Assert, horloge fixe, ne jamais modifier `tests/acceptance/`.
2. Créez la skill `.github/skills/matrice-de-tests/` : un `SKILL.md` dont la **description** dit quand l’utiliser, la méthode en quatre colonnes, et un modèle `CASES.modele.md` à côté.
3. Demandez « Prépare les tests de BookingService » **sans citer la skill**. Elle doit se charger seule : vérifiez les Références. Si elle ne se charge pas, c’est sa description qui est mauvaise.
4. Validez la matrice (`tests/CASES.md`) : tranchez chaque « ? » avant toute génération.
5. Tests unitaires paramétrés du domaine et des services, doubles injectés aux frontières (persistance, horloge).
6. Trois scénarios d’intégration, dont un **403** (supprimer la réservation d’un autre).
7. Couverture : ciblez les branches manquantes. Puis relisez **le diff des tests** avant de dire « fini ».

## Modèle à copier

```markdown
---
name: matrice-de-tests
description: Préparer ou compléter les tests de SalleLibre à partir d’une
  matrice de cas (nominal, limites, négatifs, sécurité), avant tout code de test.
---
# Matrice de tests
1. Lis la règle métier et le code concerné.
2. Remplis le modèle [CASES.modele.md](./CASES.modele.md) : 4 colonnes,
   au moins 2 cas par colonne. Marque « ? » ce qui n’est pas tranché.
3. ARRÊTE-TOI : la matrice doit être validée avant tout test.
4. Un test paramétré par règle, une ligne de table par cas.
5. Ne supprime, ne saute et n’affaiblis jamais un test existant.
```

## Livrable

- La skill se charge seule (visible dans les Références)
- Matrice en 4 colonnes validée avant génération
- Trois scénarios d’intégration, dont un 403
- Diff des tests relu, services couverts à 80 % des branches

## Pièges à observer

- Une description de skill vague (« aide pour les tests ») : elle ne se charge jamais, ou partout.
- `applyTo: "test/**"` au lieu de `"tests/**"` : le fichier n’est jamais appliqué, rien ne vous prévient.
- Des tests « verts » qui ne vérifient rien : assertion faible, vraie date du jour, mock du domaine.
- L’agent qui « fait passer » la suite en modifiant un test.

## Bonus

Changez un `<` en `<=` dans `overlaps` : au moins un test doit casser. Sinon, ajoutez la règle à la skill.

## Coincé ?

- La skill ne se charge pas ? Tapez `/matrice-de-tests` pour l’appeler à la main, puis réécrivez sa description avec les mots de votre demande.
- Le test 403 échoue ? Normal si l’API ne vérifie pas le propriétaire : gardez-le, c’est la faille du TP 5.
